# Identity Document Handling and Retention

Status: implemented in Stage 06. Retention periods are **proposals** that need
confirmation from a legal or POPIA advisor before launch (see section 7).

## 1. What is collected and why

| Data | Purpose | Where it is stored |
|------|---------|--------------------|
| Date of birth | Minimum-age rule (BR-2); compared with the ID number | `customer_profiles.date_of_birth` |
| SA ID document image or PDF (front, optional back) | Identity verification by a reviewer | Private document storage (`verification_files.storage_key`) |
| SA ID number | Structural check (13 digits, Luhn, birth date, citizenship digit); duplicate-account detection | **Not stored.** Only `HMAC-SHA256(DOCUMENT_HASH_KEY, number)` and the last 3 digits |
| Driving licence image or PDF | Licence verification by a reviewer | Private document storage |
| Licence number | Duplicate detection, display | **Not stored.** HMAC and last 3 digits only |
| Licence expiry date, licence codes | Licence must outlast the rental (BR-2) | `verification_submissions`, copied to `customer_profiles.licence_expiry_date` on approval |
| Review decision, reviewer, time, note | Accountability and customer feedback | `verification_submissions` and `audit_logs` |

We collect no more than this (POPIA minimality). In particular, the full ID number,
gender and citizenship are not stored as data fields. They are visible only on the
document image itself.

## 2. Verification rules

1. Uploading never verifies anything. A new submission is `PENDING` until an administrator decides.
2. A valid ID number format proves nothing about the person. The reviewer compares the photo, the name, and the date of birth.
3. Decisions are `APPROVED`, `REJECTED` or `REQUIRES_MORE_INFORMATION`. The last two require a note, which is shown to the customer.
4. Reviewers cannot review their own documents. Customers cannot change any verification status: there is no endpoint for it, and request bodies reject unknown fields.
5. A new submission supersedes one still pending. A new submission after approval puts the profile back to `PENDING` (BR-2).
6. The same SA ID number cannot be `APPROVED` on two accounts. A partial unique index on the HMAC enforces this, and a check at submission time gives a clear error.
7. A licence must not be expired when submitted or when approved. The reviewer may correct the expiry date printed on the card.
8. Eligibility (`GET /customers/me/eligibility`) is calculated only from these database records.

## 3. File handling

- **Accepted types:** JPEG, PNG and PDF, detected from the file's **content** (magic bytes). The file name and the client's `Content-Type` are ignored.
- **Size:** at most `MAX_DOCUMENT_BYTES` per file (default 10 MB). Larger files get `413`. A reverse proxy should also cap request size in production (Stage 18).
- **Names:** storage keys are random UUIDs generated by the server. User-supplied names are never used as paths, and keys that are not UUIDs are rejected (no path traversal).
- **Integrity:** each file's SHA-256 and size are recorded.
- **Development storage:** `backend/storage/private/` (git-ignored). Directories are created with mode `700` and files with `600`. Nothing there is served statically.
- **Production storage (Stage 18):** a private object store with encryption at rest, such as S3 with SSE in `af-south-1`, keeping data in South Africa. It plugs in behind the same `DocumentStorage` interface. **Local disk storage is not encrypted at rest**, so the development setup is not suitable for production data.
- **Failed uploads:** if a submission fails after some files were saved, those files are deleted.

## 4. Access control

| Who | Can access |
|-----|-----------|
| The customer | Their own submissions and files (`/customers/me/documents…`). Other customers' submissions return `404`, so their existence is not revealed. |
| Administrators | The review queue, submission details, and files (`/admin/verifications…`). **Every file view is written to `audit_logs`** (`verification.document_viewed`). |
| Owners, other renters, anonymous users | Nothing (`403`, `404` or `401`). |

Files are served with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.

## 5. Logging and exposure rules

- ID and licence numbers never appear in API responses (only `••••••123`), application logs, validation errors, or audit logs. Automated and end-to-end tests check this.
- Public vehicle listings never include renter data.
- Audit entries record decisions, notes and file views, never document numbers.

## 6. Keys

`DOCUMENT_HASH_KEY` (backend `.env`, at least 32 characters) keys the HMAC. Keep it
secret, back it up with the other production secrets, and **do not rotate it casually**.
A new key cannot match existing HMACs, so duplicate-ID detection would stop working
for records created before the change.

## 7. Retention (proposed; needs legal confirmation)

| Data | Proposed retention |
|------|--------------------|
| Files of `SUPERSEDED`, `REJECTED` and `REQUIRES_MORE_INFORMATION` submissions | Delete files 90 days after the decision; keep the metadata row |
| Files of the current `APPROVED` submission | While the account is active, plus the period required for insurance claims, disputes and legal obligations (to be set by the advisor) |
| All verification files after account closure | Delete within the confirmed period; keep only audit metadata |
| Audit log entries | Kept (append-only); they contain no document numbers |

Automatic deletion (a scheduled purge job) is **not implemented yet**. It is planned
once the periods are confirmed (Stage 17/18). Until then, deletion requests (POPIA
data-subject rights) are handled manually by an operator through `DocumentStorage.delete`
and the database.
